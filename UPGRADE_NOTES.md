# Upgrade Notes — Hybrid Storage Management System

The Hybrid Storage Management System was upgraded in-place while preserving its existing modular architecture and desktop GUI.

The upgrades improve automatic storage management, background execution, filesystem-event handling, database consistency, migration safety, and logging.

## 1. Implemented Storage Management Features

- Time-decay data-heat calculation using an exponential half-life.
- Separate HOT/WARM/COLD classification and SSD demotion threshold.
- Automatic promotion from SECONDARY storage to SSD for HOT files.
- Automatic demotion from SSD to SECONDARY storage when data cools sufficiently.
- Hysteresis-based placement decisions to reduce repeated SSD/HDD migrations.
- Configurable optimization interval through `OPTIMIZATION_INTERVAL_SECONDS`.
- SSD capacity checks with a configurable minimum free-space reserve.
- Cold-data SSD eviction when capacity is insufficient for a hot-data promotion.
- File-stability checks before migration to reduce the risk of moving actively changing files.
- Destination existence and file-size verification after migration.
- Rollback attempts when migration verification or database updates fail.
- Migration history containing source tier, destination tier, heat, timestamp, and migration reason.

### Current heat policy

- HOT: heat score greater than or equal to 70.
- WARM: heat score from 40 to 69.
- COLD: heat score below 40.
- SSD demotion eligibility: heat score less than or equal to 25.
- Heat half-life: 600 seconds (10 minutes).

The heat value is a logical data-activity score, not a physical temperature measurement.

## 2. Filesystem Monitoring Improvements

- Watchdog monitors both configured managed storage directories.
- Filesystem events include supported CREATE, MODIFY, DELETE, and MOVE operations.
- External edits and common editor save patterns involving temporary files and renames are handled by the filesystem-event logic.
- Replacement of a registered file can be recorded as WRITE activity and used to update its logical heat.
- File lookup uses filename and storage tier where appropriate to avoid selecting a same-named block from the wrong tier.
- Migration guards suppress filesystem events generated by the application's own migrations.
- Storage monitors check drive availability and attempt to restart when a configured drive becomes available again.
- Startup reconciliation compares database metadata with the physical files present in the configured storage folders.

### Important monitoring limitation

Watchdog filesystem notifications do not capture every ordinary Windows file READ operation. The GUI's READ/WRITE controls remain a controlled workload generator for testing and demonstration.

Comprehensive OS-level READ telemetry requires a separately configured and verified Windows auditing or instrumentation mechanism.

## 3. Headless Background Monitoring

A standalone background worker was added in `background_monitor.py`.

The worker:

- Runs without opening the CustomTkinter GUI.
- Initializes the SQLite database and reconciles physical storage state at startup.
- Discovers files in the configured SSD and secondary-storage folders.
- Starts Watchdog monitoring for both storage tiers.
- Executes periodic optimization cycles.
- Attempts to restart monitors when storage folders become available again.
- Records filesystem events, migration activity, and errors in a log file.
- Stops its observers during a graceful shutdown.

The background worker can operate independently of VS Code and the desktop GUI.

## 4. Windows Automatic Startup

Windows Task Scheduler is configured to launch the background worker at user logon.

The scheduled task uses the project's virtual-environment executable:

`venv\Scripts\pythonw.exe`

It launches `background_monitor.py` without opening a regular Python console window.

This configuration allows monitoring to start after the configured Windows user logs in, without requiring the user to manually launch the worker or keep VS Code open.

The task's actual configuration and successful startup should be verified on the target Windows computer.

## 5. Logging Improvements

The background worker uses Python's `RotatingFileHandler` for bounded log-file size.

### Current logging configuration

- Log file: `logs/background_monitor.log`
- Maximum size per log file: 2,000,000 bytes (approximately 2 MB).
- Backup files retained: 4.
- Routine optimization summaries: at most once every five minutes, or when an optimization cycle reports migrations.
- Filesystem-event records: retained when emitted by the existing event-handling code.
- Migration records: logged when migrations are reported by the optimization cycle.
- Errors: recorded with exception details.

The routine summary interval is separate from the optimizer's execution interval.

`OPTIMIZATION_INTERVAL_SECONDS` in `config.py` controls how frequently periodic optimization cycles run. The current intended setting is 60 seconds.

Reducing routine summaries limits repetitive log entries while retaining important operational records. High filesystem-event activity can still produce additional log entries.

## 6. Database Consistency and Recovery

- SQLite stores logical block metadata, access history, and migration history.
- Startup discovery registers files physically present in the managed directories.
- Startup reconciliation repairs inconsistencies between physical storage and recorded placement.
- Deleted blocks can be retained with a `DELETED` status so historical records remain available.
- Normal application views should distinguish active blocks from deleted historical records.
- A fresh local database can be created for a new computer to avoid displaying stale records from a previous machine.

### Deployment on another computer

Before running the project on another PC:

1. Configure `LOCAL_SSD_PATH` and `LOCAL_SECONDARY_PATH` in `config.py`.
2. Confirm both managed directories and their drives are accessible.
3. Back up the existing `data/hybrid_storage.db`.
4. For a clean installation, rename or remove the old database while the application and background worker are stopped.
5. Launch the application and verify that startup discovery registers files physically present on that computer.

Do not reuse the previous computer's database if an independent local dataset is required.

## 7. GUI and Analytics Improvements

- Dashboard for storage and system status.
- Storage Blocks view with block metadata and placement information.
- Migration History with source tier, destination tier, heat, reason, and timestamp.
- Live Access controls for controlled READ/WRITE workloads.
- Optimization Analytics with migration counts, promotions, demotions, heat distribution, average heat, and physical storage capacity.
- Database-backed history for reviewing storage-placement decisions.

## 8. Current Project Structure

The existing modular architecture is retained, including:

- `app.py` — CustomTkinter desktop interface.
- `background_monitor.py` — Headless background monitoring and optimization.
- `config.py` — Storage paths, thresholds, and optimizer configuration.
- `database.py` — SQLite persistence and managed-file discovery.
- `engine/` — Access monitoring, placement, migration, temperature, and tiering logic.
- `storage/` — Device management and filesystem monitoring.
- `models/` — Logical block and storage-tier models.
- `workload/` — Workload generation and trace loading.
- `system_diagnostics.py` — Environment and system diagnostics.
- `logs/` — Background-monitoring logs.
- `data/` — Local SQLite database.

## 9. Validation and Testing Status

The previously recorded validation included:

- Python syntax compilation for project modules.
- Preservation of the existing database records and migration history during schema upgrades.
- Isolated tests for heat increase, HOT classification, SSD promotion, heat decay, SSD demotion, and migration-history recording.

Subsequent Windows testing confirmed that the background worker started through Task Scheduler, monitored both configured storage folders, performed optimization cycles, and recorded physical migration activity.

The final deployment should still be tested on the target hardware for:

- Automatic startup after Windows logon.
- Filesystem-event detection during external edits.
- Safe migration of actively edited files.
- Behavior when the secondary drive is disconnected and reconnected.
- Correct database reconciliation on another computer.
- Log rotation and reduced routine-summary frequency.

## 10. Known Limitations and Future Work

The following remain separate from the currently implemented functionality unless independently added and verified:

- Comprehensive OS-level Windows file-READ telemetry.
- Predictive data placement based on workload forecasting.
- Migration-cost and latency-aware optimization.
- Extended benchmarking using representative workloads.
- A dedicated Windows service instead of Task Scheduler.
- More advanced analytics and visualizations.
- Stronger recovery and transaction safeguards for unexpected hardware or process failures.

## 11. Summary

The upgrades extend the Hybrid Storage Management System from a GUI-driven prototype into a desktop application with independent background monitoring, automatic optimization, physical SSD–secondary storage migration, database reconciliation, and Windows logon startup.

The implementation provides a foundation for evaluating dynamic storage placement based on logical data heat while preserving migration history and acknowledging the limitations of filesystem-event-based monitoring.
